Étape 01 · Définition

Architecture de Kubernetes

Kubernetes est un orchestrateur de conteneurs : il fait tourner des applications conteneurisées sur un parc de machines et maintient en permanence l'état que vous avez déclaré.

Le principe tient en une boucle. Vous écrivez ce que vous voulez, par exemple trois exemplaires de cette application. Le système compare cet état désiré à l'état réel observé sur les machines, et agit sur la différence. En boucle, sans arrêt, sans intervention.

Tout le reste, les objets, les contrôleurs, les composants que nous allons détailler, ne sont que des variations de cette même boucle appliquée à des sujets différents : des pods, des adresses réseau, des certificats, des volumes.

À retenir d'abord
Kubernetes ne construit pas les images de conteneurs et n'exécute pas les conteneurs lui-même. Il décide, il planifie et il surveille. L'exécution est déléguée à un moteur de conteneurs sur chaque nœud.
Étape 02 · Le contexte

Les Défis & l'Héritage Borg

Un conteneur isolé se gère avec une commande. Cinquante conteneurs répartis sur dix machines posent des questions auxquelles on ne peut plus répondre à la main : sur quelle machine placer celui-ci, que faire quand une machine tombe la nuit, comment passer de 3 à 30 exemplaires, comment les composants se trouvent entre eux alors que leurs adresses changent, comment déployer une nouvelle version sans coupure.

Google a affronté ces questions bien avant tout le monde avec Borg, son système interne d'ordonnancement, en production depuis le milieu des années 2000. Borg gère des milliers de machines par cellule et exécute l'essentiel des charges internes de l'entreprise.

Kubernetes, publié en 2014, en est l'héritier direct, réécrit en Go et conçu pour l'extérieur. On y retrouve les idées de Borg : regrouper des conteneurs qui partagent un contexte, ordonnancer selon les ressources demandées, surveiller par des boucles de contrôle indépendantes. Ce qui change, c'est l'API publique et l'extensibilité.

Sur le terrain
Cet héritage explique certains choix qui surprennent. Le pod, par exemple, n'a pas d'équivalent chez Docker : il vient de l'alloc de Borg, un espace réservé sur une machine dans lequel plusieurs tâches cohabitent en partageant réseau et disque.
Étape 03 · Vue d'ensemble

Deux Rôles, Une Frontière

Un cluster se divise en deux populations de machines. Le plan de contrôle décide et mémorise. Les nœuds de travail exécutent. La frontière entre les deux est une seule et unique porte : l'API server.

Plan de contrôle

Reçoit vos demandes, les valide, les stocke, décide où placer les charges et surveille les écarts. Historiquement appelé nœud maître.

décide

Nœuds de travail

Reçoivent des instructions et font tourner les conteneurs. Historiquement appelés minions, aujourd'hui workers ou simplement nœuds.

exécute

Trois règles de circulation à retenir dès maintenant, elles expliquent la moitié des pannes que vous rencontrerez :

  • Seul l'API server parle à etcd. Aucun autre composant n'a le droit d'écrire dans la base.
  • Aucun composant ne parle directement à un autre. Tous passent par l'API server, qui sert de bus central et de point d'autorisation.
  • Le trafic va des nœuds vers le plan de contrôle, jamais l'inverse par défaut. Le kubelet appelle l'API server et non le contraire.
Sur Minikube
Les deux rôles sont tenus par le même nœud : un conteneur Docker qui héberge à la fois le plan de contrôle et vos applications. La séparation logique reste entière, seule la séparation physique disparaît.
Étape 04 · Plan de contrôle

Les Quatre Composants qui Décident

kube-apiserver

La façade REST du cluster, en écoute sur le port 6443. Il authentifie, autorise, valide chaque objet puis l'écrit dans etcd. Sans lui, plus rien n'est modifiable.

la porte d'entrée

etcd

Base clé-valeur distribuée, cohérente, fondée sur l'algorithme Raft. Elle contient l'intégralité de l'état du cluster. C'est le seul élément dont la perte est irréversible.

la mémoire

kube-scheduler

Repère les pods sans nœud affecté, écarte les nœuds impossibles (filtrage), note les nœuds restants (scoring) et écrit son choix. Il ne démarre rien lui-même.

l'ordonnanceur

kube-controller-manager

Un processus qui héberge des dizaines de boucles de contrôle : nœuds, ReplicaSets, endpoints, comptes de service, jetons. Chacune corrige un type d'écart.

les correcteurs

Un cinquième composant, le cloud-controller-manager, n'apparaît que sur un cluster hébergé chez un fournisseur. Il traduit les objets Kubernetes en ressources du fournisseur : un Service de type LoadBalancer devient un répartiteur de charge réel, un nœud supprimé de l'infrastructure est retiré du cluster. Sur notre installation, il est absent, et le module 14 montrera comment Minikube le remplace.

Sur le terrain
Ces quatre composants ne sont pas des services systemd : ce sont des pods statiques décrits dans /etc/kubernetes/manifests et démarrés directement par le kubelet. C'est vrai en production comme dans le nœud Minikube, où nous irons les ouvrir au module 3.
Étape 05 · Nœuds de travail

Les Trois Composants qui Exécutent

kubelet

L'agent présent sur chaque nœud, en écoute sur le port 10250. Il demande à l'API server la liste des pods qui lui sont assignés, les fait démarrer par le runtime, remonte leur état et exécute les sondes.

le contremaître

kube-proxy

Programme les règles iptables ou IPVS du nœud pour que l'adresse virtuelle d'un Service soit redirigée vers l'un des pods qui le composent.

l'aiguilleur

Runtime de conteneurs

Le moteur qui télécharge les images et lance réellement les processus. Le kubelet lui parle par l'interface standard CRI.

le moteur

Le kubelet est le seul composant qui n'est pas conteneurisé : c'est un service systemd installé sur la machine, ou dans notre cas à l'intérieur du nœud Minikube. Il ne comprend qu'une chose, une spécification de pod, quelle qu'en soit la source : l'API server, ou un fichier posé dans /etc/kubernetes/manifests.

Depuis la version 1.24, Kubernetes ne sait plus parler à Docker directement : la couche d'adaptation dockershim a été retirée. Les runtimes utilisés aujourd'hui sont containerd et CRI-O. Docker reste parfaitement utilisable pour construire des images, et nous nous en servirons au module 5.

Étape 06 · Vocabulaire

Terminologie de Base

Six termes suffisent pour tenir une conversation. Tous les autres objets s'y raccrochent.

Pod

La plus petite unité déployable. Un ou plusieurs conteneurs qui partagent une adresse IP, des volumes et un cycle de vie.

Service

Une adresse IP et un nom DNS stables devant un groupe de pods éphémères, avec répartition de charge.

module 14

Contrôleur

Une boucle qui maintient un type d'objet conforme. ReplicaSet, Deployment, DaemonSet, Job en sont.

module 11

Namespace

Un cloisonnement logique des objets à l'intérieur d'un cluster. Support naturel des quotas et des droits.

module 7

Label & sélecteur

Des étiquettes clé-valeur, et le moyen par lequel presque tous les objets se lient entre eux.

module 6

Manifeste

Le fichier YAML qui décrit un objet. Toujours quatre champs de tête : apiVersion, kind, metadata, spec.

partout
Le geste de base
Toute la formation se ramène à écrire un manifeste, l'appliquer avec kubectl apply -f, puis observer l'écart entre ce qu'on a demandé et ce qui s'est passé avec kubectl get et kubectl describe.
Étape 07 · Le trajet

Que se Passe-t-il Quand Vous Créez un Pod ?

  • 1. kubectl transforme votre YAML en requête HTTPS vers l'API server, avec votre certificat client.
  • 2. L'API server vous authentifie, vérifie vos droits (RBAC), fait passer l'objet dans les contrôleurs d'admission, valide le schéma, puis écrit dans etcd. À cet instant, le pod existe mais n'est nulle part.
  • 3. Le scheduler, qui surveille les pods sans nœud, filtre les nœuds candidats, les note, choisit le meilleur et écrit ce choix dans l'objet pod.
  • 4. Le kubelet du nœud concerné voit qu'un pod lui est assigné. Il demande au runtime de télécharger les images et de démarrer les conteneurs.
  • 5. Le kubelet remonte l'état à l'API server, qui l'écrit dans etcd. kubectl get pods affiche Running.
Sur le terrain
Retenez ce trajet, c'est votre grille de dépannage du module 16. Un pod bloqué en Pending n'a pas franchi l'étape 3 : le problème est un ordonnancement impossible. Un pod en ImagePullBackOff est bloqué à l'étape 4 : le problème est le runtime ou le registre.
Étape 08 · Dimensionnement

Recommandations de Ressources

Les besoins d'un plan de contrôle croissent avec le nombre d'objets et le rythme des changements, pas avec la charge applicative. Le facteur limitant est presque toujours etcd, qui écrit sur disque de façon synchrone à chaque modification.

Formation

2 vCPU et 2 Go alloués au nœud Minikube. Suffisant pour l'intégralité des ateliers de ces trois jours.

notre VM

Production modeste

Plan de contrôle sur 3 machines, 4 vCPU et 8 à 16 Go chacune, disque SSD à faible latence d'écriture pour etcd.

jusqu'à ~50 nœuds

Limites du projet

5 000 nœuds, 150 000 pods, 110 pods par nœud par défaut. Bien au-delà des besoins réels de la plupart des organisations.

plafonds
Deux règles de dimensionnement
Le nombre de nœuds du plan de contrôle doit être impair (3 ou 5) parce qu'etcd fonctionne au quorum. Et un plan de contrôle qui tombe n'arrête pas les applications en cours : les pods continuent de tourner, mais plus rien ne peut être modifié ni réparé.
Étape 09 · QCM

Vérifiez vos Acquis

QUESTION 01
Le scheduler démarre les conteneurs sur le nœud qu'il a choisi.
Il écrit, c'est tout

Le scheduler se contente d'inscrire un nom de nœud dans l'objet pod. C'est le kubelet de ce nœud qui, voyant son nom, demande le démarrage au runtime.

QUESTION 02
Si etcd est perdu sans sauvegarde, le cluster est irrécupérable.
La seule perte définitive

etcd contient tout l'état déclaré. Les binaires se réinstallent, les nœuds se rejoignent, mais un etcd perdu signifie un cluster à reconstruire. La sauvegarde d'etcd est la première tâche d'exploitation à automatiser.

QUESTION 03
Kubernetes a besoin de Docker pour faire tourner des conteneurs.
Retiré en 1.24

Le kubelet dialogue avec un runtime conforme à l'interface CRI, en pratique containerd ou CRI-O. Docker reste utile pour construire des images, mais il n'est plus dans la chaîne d'exécution.

QUESTION 04
Un plan de contrôle arrêté ne coupe pas les applications déjà en cours.
Elles survivent

Les kubelets continuent de faire tourner les pods existants et de les redémarrer localement. En revanche, plus aucune création, mise à jour ni replanification n'est possible tant que l'API server est absent.

Étape 10 · Atelier

Atelier 2 : la Vie Sans Orchestrateur

Atelier 02 · 30 minutes

Manipuler des conteneurs à la main, et mesurer ce qui manque

Avant d'installer Kubernetes, faisons son travail nous-mêmes. Chaque limite rencontrée ici correspond à une fonctionnalité que le module 3 va apporter.

1. Trois copies d'une application
$ docker run -d --name saucisse1 -p 8080:80 nginx:1.27 $ docker run -d --name saucisse2 -p 8081:80 nginx:1.27 Que se passe-t-il si on reutilise le meme port ? Lisez l'erreur. $ docker run -d --name saucisse3 -p 8080:80 nginx:1.27 $ docker ps $ curl -s -o /dev/null -w "%{http_code}\n" localhost:8080 localhost:8081
2. Ce qu'est réellement l'isolation
Un conteneur est un processus ordinaire de la VM $ PID=$(docker inspect -f '{{.State.Pid}}' saucisse1) ; echo $PID $ ps -p $PID -o pid,user,comm Les espaces de noms : ce que le processus voit $ sudo lsns -p $PID Les cgroups : ce qu'il a le droit de consommer $ cat /proc/$PID/cgroup Une adresse IP par conteneur, sur un pont prive $ docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' saucisse1 saucisse2
3. Personne ne surveille
On tue le processus principal du conteneur $ sudo kill -9 $PID Attendu : saucisse1 est Exited, et rien ne le relance $ docker ps -a | grep saucisse1 $ curl -s -o /dev/null -w "%{http_code}\n" localhost:8080
4. Le bilan, puis on nettoie

Quatre limites viennent d'apparaître, notez-les : les ports se disputent sur la machine hôte, aucune redirection ne répartit le trafic entre les copies, rien ne relance ce qui meurt, et tout ceci ne concerne qu'une seule machine. Kubernetes répond exactement à ces quatre points.

$ docker rm -f saucisse1 saucisse2 2>/dev/null ; docker ps -a
Étape 11 · Conclusion

Récapitulatif du Module 2

  • Boucle de contrôle : état désiré comparé à l'état réel, correction permanente de l'écart.
  • Plan de contrôle : API server (la porte), etcd (la mémoire), scheduler (le placement), controller-manager (les correcteurs).
  • Nœud : kubelet (l'agent), kube-proxy (les règles réseau), runtime CRI (l'exécution).
  • Circulation : tout passe par l'API server, seul lui écrit dans etcd, les nœuds appellent le plan de contrôle.
  • Trajet d'un pod : kubectl, API server, etcd, scheduler, kubelet, runtime. C'est aussi la grille de dépannage.
