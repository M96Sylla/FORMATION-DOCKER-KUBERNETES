Étape 01 · Le rappel

Sécurité des Charges & du Réseau

Un conteneur n'est pas une machine virtuelle. C'est un processus de la machine hôte, isolé par des mécanismes du noyau, et il partage ce noyau avec tous les autres. L'atelier 2 l'a montré : le processus apparaissait dans un simple ps sur la VM.

La conséquence est directe. Un conteneur qui tourne en root avec des privilèges étendus est, à quelques barrières près, root sur le nœud. Il peut monter le système de fichiers de l'hôte, lire les certificats du kubelet, et de là prendre le contrôle du cluster.

Deux mécanismes traitent ce risque : le contexte de sécurité, qui contraint chaque pod, et l'admission de sécurité des pods, qui impose un niveau minimal à tout un namespace. La seconde moitié du module traite du réseau, où la situation par défaut est tout aussi ouverte.

Étape 02 · Le conteneur

Contextes de Sécurité

Le securityContext se déclare au niveau du pod (il s'applique alors à tous ses conteneurs) ou au niveau d'un conteneur, qui l'emporte en cas de conflit.

spec: securityContext: # niveau pod runAsNonRoot: true runAsUser: 10001 fsGroup: 10001 # groupe proprietaire des volumes montes seccompProfile: { type: RuntimeDefault } containers: - name: app securityContext: # niveau conteneur, prioritaire allowPrivilegeEscalation: false readOnlyRootFilesystem: true capabilities: drop: ["ALL"] add: ["NET_BIND_SERVICE"] # uniquement si port < 1024

Les quatre réglages qui comptent, par ordre d'efficacité : ne pas tourner en root, interdire l'élévation de privilèges, abandonner toutes les capacités puis n'en ajouter que le strict nécessaire, et monter la racine en lecture seule. Ce dernier point impose de déclarer un emptyDir pour les répertoires temporaires, ce qui est une bonne discipline en soi.

Sur le terrain
Le drapeau privileged: true désactive pratiquement toutes les protections et donne au conteneur un accès direct aux périphériques du nœud. Il a des usages légitimes, presque tous du côté des agents d'infrastructure. Sur une application métier, c'est un signal d'alerte qui mérite une question en revue de code.
Étape 03 · Le namespace

Stratégies de Sécurité des Pods

Déclarer un bon contexte de sécurité reste facultatif, donc oublié. L'admission de sécurité des pods impose un niveau à tout un namespace, par de simples étiquettes. Elle remplace les anciennes PodSecurityPolicy, supprimées de Kubernetes depuis la version 1.25.

privileged

Aucune restriction. Réservé aux namespaces d'infrastructure qui hébergent des agents système.

tout permis

baseline

Interdit les élévations connues : mode privilégié, espaces de noms de l'hôte, capacités dangereuses. Compatible avec la plupart des images existantes.

le minimum

restricted

Applique les bonnes pratiques de durcissement : non-root obligatoire, aucune capacité, pas d'élévation, profil seccomp. Exige des images conçues pour.

la cible
Trois modes, combinables : refuser, avertir, journaliser $ kubectl label ns production pod-security.kubernetes.io/enforce=restricted $ kubectl label ns production pod-security.kubernetes.io/warn=restricted $ kubectl label ns production pod-security.kubernetes.io/audit=restricted
La méthode de migration
On ne pose jamais enforce en premier sur un namespace existant, sous peine de bloquer tous les déploiements. On commence par warn et audit, on lit les avertissements pendant quelques semaines, on corrige les manifestes, et on bascule enforce seulement quand plus rien ne remonte.
Étape 04 · Le réseau

Politiques de Sécurité Réseau

Voici la situation par défaut, et elle surprend toujours : tout pod peut joindre tout autre pod du cluster, sur n'importe quel port, dans n'importe quel namespace. Le réseau est entièrement plat et ouvert. Une application compromise en zone publique peut donc parler directement à la base de données de la comptabilité.

La NetworkPolicy est l'objet qui referme cela. Son fonctionnement repose sur trois règles à mémoriser ensemble :

  • Une politique sélectionne des pods par leurs étiquettes. Les pods non sélectionnés ne sont pas concernés.
  • Dès qu'un pod est sélectionné par au moins une politique, il passe en mode refus par défaut pour la direction concernée (entrée ou sortie).
  • Les politiques sont additives, comme RBAC. Elles n'interdisent rien, elles autorisent. L'union de toutes les règles qui visent un pod définit ce qui passe.
Sur le terrain
Une NetworkPolicy n'a d'effet que si le plugin CNI l'implémente. Certains l'acceptent sans jamais l'appliquer, ce qui donne l'illusion parfaite d'un cluster protégé. C'est exactement pour cette raison que nous avons imposé --cni=calico au module 3. Sur un cluster inconnu, testez toujours une politique de refus avant de faire confiance à la suivante.
Étape 05 · Les manifestes

Refus par Défaut, puis Ouvertures

1. La politique fondatrice : tout refuser en entree dans le namespace apiVersion: networking.k8s.io/v1 kind: NetworkPolicy metadata: { name: refus-par-defaut, namespace: saucisse } spec: podSelector: {} # selecteur vide = TOUS les pods du namespace policyTypes: [Ingress] # aucune regle 'ingress' : donc rien n'est autorise --- 2. L'ouverture ciblee : seule l'application joint la base, sur le port 3306 kind: NetworkPolicy metadata: { name: app-vers-base, namespace: saucisse } spec: podSelector: matchLabels: { app: mysql } # qui est protege policyTypes: [Ingress] ingress: - from: - podSelector: matchLabels: { app: saucisse } # qui a le droit ports: - { protocol: TCP, port: 3306 } # sur quel port
Deux pièges classiques
Fermer la sortie d'un pod sans autoriser le port 53 casse la résolution DNS, et l'application semble alors victime d'une panne réseau incompréhensible. Et un namespaceSelector combiné à un podSelector dans le même élément de liste signifie « ce pod dans ce namespace », alors que deux éléments séparés signifient « l'un ou l'autre ». Un tiret mal placé ouvre bien plus que prévu.
Étape 06 · QCM

Vérifiez vos Acquis

QUESTION 01
Sans NetworkPolicy, tout pod peut joindre tout autre pod du cluster.
Ouvert par défaut

Le modèle réseau impose la connectivité totale. Le cloisonnement est une couche à ajouter explicitement, namespace par namespace.

QUESTION 02
Les PodSecurityPolicy sont le mécanisme actuel de durcissement des pods.
Supprimées en 1.25

Elles ont été remplacées par l'admission de sécurité des pods, pilotée par des étiquettes de namespace et trois niveaux prédéfinis.

QUESTION 03
Une NetworkPolicy peut être acceptée par l'API sans jamais être appliquée.
Dépend du CNI

L'objet est stocké quel que soit le plugin réseau. Si celui-ci n'implémente pas les politiques, rien n'est filtré et le cluster paraît protégé à tort.

QUESTION 04
readOnlyRootFilesystem empêche l'application d'écrire ses fichiers temporaires.
Il suffit d'un volume

On monte un emptyDir sur /tmp et sur les répertoires de travail. La racine reste protégée, l'application écrit là où on l'autorise.

Étape 07 · Atelier

Atelier 13 : Durcir les Pods

Atelier 13 · Partie 1 · 25 minutes

Contexte de sécurité, puis niveau restricted imposé au namespace

1. Constater le comportement par défaut
$ kubectl run root-par-defaut --image=nginx:1.27 Attendu : uid=0, l'application tourne en root $ kubectl exec root-par-defaut -- id Et elle peut ecrire partout dans son systeme de fichiers $ kubectl exec root-par-defaut -- touch /etc/preuve && echo "ecriture possible"
2. Le même service, durci
$ cd ~/k8s && cat > durci.yaml <<'EOF' apiVersion: v1 kind: Pod metadata: { name: durci } spec: securityContext: runAsNonRoot: true runAsUser: 10001 seccompProfile: { type: RuntimeDefault } containers: - name: app image: saucisse:v1 imagePullPolicy: Never securityContext: allowPrivilegeEscalation: false readOnlyRootFilesystem: true capabilities: { drop: ["ALL"] } volumeMounts: [{ name: tmp, mountPath: /tmp }] volumes: [{ name: tmp, emptyDir: {} }] EOF $ kubectl apply -f durci.yaml $ kubectl exec durci -- id Attendu : echec, le systeme de fichiers racine est en lecture seule $ kubectl exec durci -- touch /preuve
3. Imposer le niveau au namespace entier
$ kubectl create namespace coffre $ kubectl label ns coffre \ pod-security.kubernetes.io/enforce=restricted \ pod-security.kubernetes.io/warn=restricted Attendu : creation refusee, avec la liste precise des manquements $ kubectl run refuse -n coffre --image=nginx:1.27 Le pod durci, lui, passe $ kubectl apply -n coffre -f durci.yaml $ kubectl get pods -n coffre
Étape 08 · Atelier

Atelier 13 : Cloisonner le Réseau

Atelier 13 · Partie 2 · 30 minutes

Du réseau ouvert au refus par défaut, puis à l'ouverture ciblée

1. Le décor
$ kubectl -n saucisse run serveur --image=nginx:1.27 --labels=app=serveur $ kubectl -n saucisse expose pod serveur --port=80 $ kubectl -n saucisse run autorise --image=nicolaka/netshoot --labels=app=saucisse \ --command -- sleep 3600 $ kubectl -n saucisse run intrus --image=nicolaka/netshoot --labels=app=inconnu \ --command -- sleep 3600 Sans politique, les deux passent $ kubectl -n saucisse exec autorise -- curl -s -m3 -o /dev/null -w "%{http_code}\n" serveur $ kubectl -n saucisse exec intrus -- curl -s -m3 -o /dev/null -w "%{http_code}\n" serveur
2. Tout refuser
$ cat > refus.yaml <<'EOF' apiVersion: networking.k8s.io/v1 kind: NetworkPolicy metadata: { name: refus-par-defaut, namespace: saucisse } spec: podSelector: {} policyTypes: [Ingress] EOF $ kubectl apply -f refus.yaml Attendu : les deux appels expirent maintenant $ kubectl -n saucisse exec autorise -- curl -s -m3 -o /dev/null -w "%{http_code}\n" serveur $ kubectl -n saucisse exec intrus -- curl -s -m3 -o /dev/null -w "%{http_code}\n" serveur
3. Ouvrir pour une seule étiquette
$ cat > ouverture.yaml <<'EOF' apiVersion: networking.k8s.io/v1 kind: NetworkPolicy metadata: { name: saucisse-vers-serveur, namespace: saucisse } spec: podSelector: matchLabels: { app: serveur } policyTypes: [Ingress] ingress: - from: - podSelector: matchLabels: { app: saucisse } ports: - { protocol: TCP, port: 80 } EOF $ kubectl apply -f ouverture.yaml Attendu : 200 pour l'un, expiration pour l'autre $ kubectl -n saucisse exec autorise -- curl -s -m3 -o /dev/null -w "%{http_code}\n" serveur $ kubectl -n saucisse exec intrus -- curl -s -m3 -o /dev/null -w "%{http_code}\n" serveur $ kubectl -n saucisse describe networkpolicy saucisse-vers-serveur
4. Le piège du DNS
On ferme aussi les sorties du pod autorise $ kubectl -n saucisse apply -f - <<'EOF' apiVersion: networking.k8s.io/v1 kind: NetworkPolicy metadata: { name: sortie-fermee, namespace: saucisse } spec: podSelector: { matchLabels: { app: saucisse } } policyTypes: [Egress] EOF Le nom ne se resout plus : la panne ressemble a tout sauf a du filtrage $ kubectl -n saucisse exec autorise -- curl -s -m3 serveur Corrigez en autorisant le port 53 vers kube-system, puis retestez $ kubectl -n saucisse delete networkpolicy sortie-fermee
Validation

Vous devez pouvoir montrer les trois états successifs du même appel : autorisé, expiré, puis autorisé pour un pod et refusé pour l'autre. Et savoir expliquer en une phrase pourquoi fermer les sorties sans ouvrir le port 53 rend un cluster incompréhensible.

Étape 09 · Conclusion

Récapitulatif du Module 13

  • Le noyau est partagé. Un conteneur privilégié en root est presque root sur le nœud.
  • Contexte de sécurité : non-root, pas d'élévation, aucune capacité, racine en lecture seule. Déclarable au niveau du pod ou du conteneur.
  • Admission de sécurité des pods : trois niveaux, trois modes, posés par étiquettes de namespace. Elle remplace les PodSecurityPolicy supprimées.
  • Migration : warn et audit d'abord, enforce seulement quand plus rien ne remonte.
  • NetworkPolicy : additive, sélective, et sans effet si le plugin CNI ne l'implémente pas. Refus par défaut, puis ouvertures ciblées, sans oublier le DNS.
