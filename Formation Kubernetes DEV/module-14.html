Étape 01 · Le problème

Exposer : les Services

Les pods sont éphémères et leurs adresses changent à chaque recréation. Une application qui écrirait en dur l'adresse d'un autre pod tomberait en panne au premier redémarrage, à la première mise à jour, à la première montée en charge.

Le Service résout cela en fournissant une adresse IP virtuelle et un nom DNS stables devant un groupe de pods variable. Il répartit en plus les connexions entre eux.

Le lien entre le Service et ses pods ne se fait ni par nom ni par adresse, mais par étiquettes. C'est ce couplage souple qui permet aux pods d'aller et venir sans que rien ne change côté appelant.

Le vocabulaire des ports
port est le port du Service, celui que l'on appelle. targetPort est le port du conteneur, celui qui écoute. nodePort est le port ouvert sur chaque nœud, entre 30000 et 32767. Les confondre est la première cause de service qui ne répond pas.
Étape 02 · Le mécanisme

Schéma de Fonctionnement

  • 1. Le Service déclare un selector, par exemple app: saucisse.
  • 2. Un contrôleur surveille les pods qui portent ces étiquettes et dont la sonde de disponibilité répond. Il maintient à jour la liste de leurs adresses dans des objets EndpointSlice.
  • 3. Sur chaque nœud, kube-proxy lit cette liste et programme des règles de réécriture, en iptables, IPVS ou nftables selon sa configuration.
  • 4. Un paquet destiné à l'adresse virtuelle du Service est réécrit vers l'un des pods, choisi au hasard, avant même de sortir de la machine émettrice.

Deux conséquences pratiques. Il n'existe aucun processus mandataire par lequel le trafic transiterait : c'est du filtrage de paquets, sans point de passage unique et sans goulot d'étranglement. Et la répartition se fait par connexion, pas par requête HTTP : dix requêtes dans une même connexion persistante iront toutes au même pod.

Sur le terrain
Un pod dont la readinessProbe échoue est immédiatement retiré des EndpointSlices et cesse de recevoir du trafic, sans être détruit. C'est le lien direct entre le module 6 et celui-ci : la sonde de disponibilité est le mécanisme qui pilote la mise en service, et l'objet EndpointSlice est le premier endroit à regarder quand un service ne répond plus.
Étape 03 · Type 1

ClusterIP

Le type par défaut, et de loin le plus utilisé. Il attribue une adresse virtuelle joignable uniquement depuis l'intérieur du cluster, plus un nom DNS. C'est la brique de communication entre services.

apiVersion: v1 kind: Service metadata: { name: saucisse } spec: type: ClusterIP # valeur par defaut, peut etre omise selector: { app: saucisse } ports: - port: 80 # ce que l'on appelle targetPort: 8080 # ce qui ecoute dans le conteneur sessionAffinity: ClientIP # optionnel : toujours le meme pod par client

Une variante mérite d'être connue : le service sans tête, déclaré avec clusterIP: None. Il n'attribue aucune adresse virtuelle et ne répartit rien. Le DNS renvoie directement toutes les adresses des pods. C'est ce qu'utilisent les StatefulSets, et ce dont ont besoin les grappes de bases de données qui veulent connaître chacun de leurs membres.

Étape 04 · Types 2 et 3

NodePort & LoadBalancer

NodePort

Ouvre le même port sur tous les nœuds, entre 30000 et 32767. Une connexion sur ce port, quel que soit le nœud, est redirigée vers le Service. Simple, mais les ports sont laids et le client doit connaître l'adresse d'un nœud.

accès direct

LoadBalancer

Demande à l'infrastructure de fournir un répartiteur de charge externe avec une adresse publique. Chez un fournisseur cloud, le cloud-controller-manager le crée. Sur une infrastructure interne, il faut un composant comme MetalLB.

production

Ces types sont cumulatifs : un LoadBalancer alloue aussi un NodePort, qui repose lui-même sur une ClusterIP. Le type ne remplace pas le précédent, il l'enveloppe.

Sans fournisseur d'adresses, un Service de type LoadBalancer reste indéfiniment en Pending dans la colonne EXTERNAL-IP. Ce n'est pas une panne, c'est l'absence de composant capable de répondre à la demande.

Sur notre cluster
Minikube fournit deux réponses. minikube service NOM ouvre un accès direct depuis la VM vers un NodePort. Et minikube tunnel, lancé dans un terminal séparé et laissé actif, attribue de vraies adresses externes aux Services de type LoadBalancer. C'est ce qui remplace le cloud-controller-manager absent.
Étape 05 · Cas particuliers

ExternalName & Service Sans Sélecteur

Deux formes servent à faire entrer une ressource extérieure au cluster dans son espace de noms, ce qui permet aux applications de l'appeler comme n'importe quel service interne.

1. ExternalName : un simple alias DNS, aucune adresse, aucun proxy kind: Service metadata: { name: base-historique } spec: type: ExternalName externalName: db.interne.exemple.fr --- 2. Service sans selecteur : on fournit les adresses a la main kind: Service metadata: { name: base-legacy } spec: ports: [{ port: 3306 }] # pas de selector : rien ne se remplit tout seul --- apiVersion: discovery.k8s.io/v1 kind: EndpointSlice metadata: name: base-legacy-1 labels: { kubernetes.io/service-name: base-legacy } addressType: IPv4 ports: [{ port: 3306 }] endpoints: [{ addresses: ["10.20.30.40"] }]
Quand s'en servir
C'est l'outil des migrations. L'application appelle base-legacy depuis le premier jour. Tant que la base tourne encore sur un serveur physique, le service pointe vers son adresse. Le jour où elle entre dans le cluster, on ajoute un sélecteur et on supprime les adresses manuelles : le code applicatif n'a pas changé d'une ligne.
Étape 06 · QCM

Vérifiez vos Acquis

QUESTION 01
Le trafic d'un Service transite par un processus mandataire dédié.
Des règles, pas un proxy

kube-proxy programme des règles de réécriture dans le noyau. Le paquet est redirigé avant de quitter la machine émettrice, sans point de passage central.

QUESTION 02
Un pod dont la readinessProbe échoue est retiré des destinataires du Service.
Le lien direct

Le contrôleur ne retient que les pods prêts dans les EndpointSlices. C'est le premier objet à consulter quand un service ne répond plus.

QUESTION 03
Un Service de type LoadBalancer alloue aussi un NodePort et une ClusterIP.
Types cumulatifs

Chaque type enveloppe le précédent. C'est pourquoi un LoadBalancer reste joignable de l'intérieur par son nom DNS habituel.

QUESTION 04
Un Service répartit la charge requête par requête.
Par connexion

La décision est prise à l'ouverture de la connexion. Une connexion HTTP persistante enverra toutes ses requêtes au même pod, ce qui déséquilibre souvent le trafic gRPC.

Étape 07 · Atelier

Atelier 14 : ClusterIP et Découverte

Atelier 14 · Partie 1 · 25 minutes

Exposer saucisse à l'intérieur du cluster, et observer les destinataires

1. Créer le service
$ kubectl get deploy saucisse $ kubectl expose deployment saucisse --port=80 --target-port=8080 $ kubectl get svc saucisse La liste des pods reellement joignables $ kubectl get endpointslices -l kubernetes.io/service-name=saucisse -o wide
2. La répartition, vue de l'intérieur
Par le nom court, depuis un pod du meme namespace $ kubectl exec n1 -- curl -s http://saucisse Dix appels : les noms d'hote doivent varier $ kubectl exec n1 -- sh -c 'for i in $(seq 10); do curl -s http://saucisse; done' | sort | uniq -c Le nom complet et l'entree DNS $ kubectl exec n1 -- nslookup saucisse.default.svc.cluster.local
3. Le lien avec la sonde de disponibilité
On casse la readiness d'un seul pod, en changeant son etiquette $ POD=$(kubectl get pod -l app=saucisse -o jsonpath='{.items[0].metadata.name}') $ kubectl label pod $POD app=hors-service --overwrite Le pod tourne toujours, mais il a quitte le service $ kubectl get pods -l app=saucisse $ kubectl get endpointslices -l kubernetes.io/service-name=saucisse -o wide Et le Deployment en a cree un nouveau pour tenir le compte $ kubectl get pods -L app $ kubectl delete pod $POD
Étape 08 · Atelier

Atelier 14 : Sortir du Cluster

Atelier 14 · Partie 2 · 30 minutes

NodePort, LoadBalancer et ExternalName

1. NodePort
$ kubectl expose deployment saucisse --name=saucisse-np --type=NodePort \ --port=80 --target-port=8080 $ kubectl get svc saucisse-np Le port attribue, entre 30000 et 32767 $ PORT=$(kubectl get svc saucisse-np -o jsonpath='{.spec.ports[0].nodePort}') $ curl -s http://$(minikube ip):$PORT Le raccourci Minikube, qui ouvre l'acces et affiche l'URL $ minikube service saucisse-np --url
2. LoadBalancer
$ kubectl expose deployment saucisse --name=saucisse-lb --type=LoadBalancer \ --port=80 --target-port=8080 Attendu : EXTERNAL-IP reste en Pending, faute de fournisseur $ kubectl get svc saucisse-lb Dans un SECOND terminal, laissez tourner (mot de passe sudo demande) $ minikube tunnel De retour dans le premier terminal $ kubectl get svc saucisse-lb $ curl -s http://$(kubectl get svc saucisse-lb -o jsonpath='{.status.loadBalancer.ingress[0].ip}')
3. Un service sans tête, et un alias externe
Sans tete : le DNS renvoie toutes les adresses de pods $ kubectl create service clusterip saucisse-direct --clusterip="None" --tcp=80:8080 $ kubectl patch svc saucisse-direct -p '{"spec":{"selector":{"app":"saucisse"}}}' $ kubectl exec n1 -- nslookup saucisse-direct.default.svc.cluster.local Alias vers un service exterieur au cluster $ kubectl create service externalname horloge --external-name=time.cloudflare.com $ kubectl exec n1 -- nslookup horloge.default.svc.cluster.local
4. Diagnostic d'un service muet
Un selecteur qui ne correspond a rien : la panne la plus frequente $ kubectl patch svc saucisse -p '{"spec":{"selector":{"app":"faute-de-frappe"}}}' Le service existe, mais sa liste de destinataires est vide $ kubectl get endpointslices -l kubernetes.io/service-name=saucisse $ kubectl exec n1 -- curl -s -m3 http://saucisse || echo "aucune reponse" $ kubectl patch svc saucisse -p '{"spec":{"selector":{"app":"saucisse"}}}'
Validation

Vous devez pouvoir joindre saucisse par trois chemins (nom interne, NodePort, LoadBalancer via le tunnel) et savoir diagnostiquer un service dont la liste de destinataires est vide. Conservez le service saucisse et le Deployment site du module 9 pour le module 15.

Étape 09 · Conclusion

Récapitulatif du Module 14

  • Le Service fournit une adresse et un nom stables devant des pods éphémères, liés par étiquettes.
  • Mécanisme : selector, EndpointSlices tenus à jour selon la readiness, règles programmées par kube-proxy. Aucun mandataire, répartition par connexion.
  • ClusterIP pour l'interne, avec la variante sans tête pour connaître chaque pod individuellement.
  • NodePort ouvre un port sur tous les nœuds, LoadBalancer demande une adresse externe. Les types sont cumulatifs.
  • ExternalName et service sans sélecteur font entrer une ressource externe dans l'espace de noms du cluster, ce qui est l'outil des migrations.
