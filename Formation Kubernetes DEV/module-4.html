Étape 01 · Le contrat

Le Réseau du Cluster

Kubernetes n'implémente aucun réseau. Il impose un contrat et laisse un plugin le réaliser. Ce contrat tient en trois exigences, et tout le reste en découle.

  • Tout pod peut joindre tout autre pod, sur n'importe quel nœud, sans traduction d'adresse.
  • Tout nœud peut joindre tout pod du cluster, et réciproquement, sans NAT.
  • L'adresse qu'un pod voit de lui-même est celle que les autres voient. Pas d'adresse interne différente de l'adresse externe.

Ces règles semblent anodines. Elles éliminent en réalité toute la complexité des correspondances de ports rencontrée à l'atelier 2, et rendent le réseau du cluster aussi simple à raisonner qu'un réseau plat de machines.

Étape 02 · Le fondement

Une IP Unique par Pod

Chaque pod reçoit sa propre adresse IP, prise dans la plage attribuée au nœud. Cette adresse est portée par un espace de noms réseau que tous les conteneurs du pod partagent. Concrètement, deux conteneurs d'un même pod se parlent sur localhost, comme deux processus sur une même machine.

Trois conséquences directes pour votre travail quotidien :

  • Deux conteneurs d'un même pod ne peuvent pas écouter sur le même port. Ils partagent la pile réseau.
  • Deux pods différents, eux, peuvent parfaitement écouter tous les deux sur le port 80, puisqu'ils ont des adresses distinctes. C'est exactement ce que l'atelier 2 ne savait pas faire.
  • Le champ containerPort d'un manifeste est purement documentaire. Il n'ouvre ni ne ferme rien, contrairement à la publication de port de Docker.
Le point crucial
Cette adresse est éphémère. Elle disparaît avec le pod et le suivant en recevra une autre. C'est précisément pour cela que le Service existe (module 14) : aucune application ne doit jamais écrire en dur l'adresse IP d'un pod.
Étape 03 · Les chemins

Quatre Types de Communication

01

Conteneur vers conteneur

Dans le même pod, via localhost et un port. Aucun réseau traversé, aucune latence. C'est le fondement des patterns du module 8.

02

Pod vers pod

Directement d'IP à IP, sur le même nœud par une paire d'interfaces virtuelles, entre nœuds par le plugin CNI qui se charge du transport.

03

Pod vers Service

Le pod contacte une IP virtuelle stable. kube-proxy réécrit la destination vers l'un des pods membres, choisi au hasard.

04

Extérieur vers cluster

Par un NodePort, un LoadBalancer ou un Ingress. Les seuls points d'entrée depuis le monde extérieur, détaillés aux modules 14 et 15.

Entre nœuds, le plugin doit acheminer un paquet destiné à une adresse de pod qui n'appartient à aucun réseau physique. Deux familles de solutions : l'encapsulation (VXLAN ou IP-in-IP, le paquet voyage dans un paquet), et le routage natif (les nœuds s'échangent les routes, souvent par BGP). Calico, notre plugin, sait faire les deux.

Étape 04 · L'interface

CNI : Container Network Interface

CNI est une spécification de la CNCF, volontairement minimale. Elle définit un contrat entre le runtime et un exécutable : quand un pod est créé, le runtime appelle un binaire en lui passant l'espace de noms réseau du pod et une configuration JSON. Le binaire crée l'interface, attribue une adresse, pose les routes et rend le résultat. À la destruction, il nettoie.

Deux emplacements sur le nœud suffisent à tout comprendre :

  • /etc/cni/net.d/ contient les fichiers de configuration, lus par ordre alphabétique. Le premier valide gagne.
  • /opt/cni/bin/ contient les binaires appelés par le runtime.
/etc/cni/net.d/10-calico.conflist, forme simplifiee { "name": "k8s-pod-network", "cniVersion": "0.3.1", "plugins": [ { "type": "calico", # attribue l'IP et cree l'interface "ipam": { "type": "calico-ipam" } }, { "type": "portmap" } # gere hostPort si demande ] }
Sur le terrain
Un fichier de configuration CNI absent ou invalide provoque exactement deux symptômes : le nœud reste NotReady, et les pods se bloquent en ContainerCreating avec une erreur mentionnant le réseau. Ce répertoire est le premier endroit à inspecter face à un problème réseau généralisé.
Étape 05 · Les plages

Les Trois Plages d'Adresses

Un cluster manipule trois espaces d'adressage distincts, qui ne doivent jamais se chevaucher entre eux ni avec le réseau de l'entreprise.

Réseau des nœuds

Les adresses réelles des machines. Ici, le réseau Docker de votre VM, que minikube ip vous donne.

ex. 192.168.49.0/24

Réseau des pods

Fixé à l'installation du cluster. Découpé en sous-réseaux, un par nœud, visible dans .spec.podCIDR.

ex. 10.244.0.0/16

Réseau des services

Fixé par --service-cluster-ip-range sur l'API server. Adresses purement virtuelles, sans interface associée nulle part.

défaut 10.96.0.0/12

Une adresse de Service n'existe sur aucune carte réseau. Un ping vers elle échoue le plus souvent alors que le service fonctionne parfaitement : ce n'est qu'une entrée dans des règles de réécriture, appliquées au premier paquet TCP ou UDP sortant. Tester un service avec ping est une erreur de diagnostic classique.

À vérifier avant toute installation
Un chevauchement entre le réseau des pods et un réseau de l'entreprise produit des pannes intermittentes et très difficiles à identifier. Ces plages se choisissent avant la création du cluster, car les changer ensuite impose de le reconstruire.
Étape 06 · Résolution de noms

CoreDNS & la Découverte

Chaque cluster embarque un serveur DNS interne, CoreDNS, déployé dans le namespace kube-system et exposé par un Service nommé kube-dns, traditionnellement à l'adresse 10.96.0.10.

Le kubelet injecte cette adresse dans le /etc/resolv.conf de chaque pod, avec une liste de suffixes de recherche. Résultat : un pod peut joindre un service par un nom court dans son propre namespace, ou par un nom complet ailleurs.

Format canonique d'un nom de service <service>.<namespace>.svc.cluster.local Depuis un pod du namespace 'default' curl http://mysql # meme namespace curl http://mysql.prod # namespace 'prod' curl http://mysql.prod.svc.cluster.local # nom complet /etc/resolv.conf genere dans chaque pod nameserver 10.96.0.10 search default.svc.cluster.local svc.cluster.local cluster.local options ndots:5
Sur le terrain
L'option ndots:5 impose que tout nom comportant moins de cinq points soit d'abord essayé avec chaque suffixe de recherche. Un appel vers api.exemple.com déclenche donc trois requêtes inutiles avant la bonne. Sur une application bavarde, c'est une cause classique de latence et de surcharge de CoreDNS. Le correctif consiste à écrire le nom avec un point final, ou à ajuster dnsConfig dans le pod.
Étape 07 · QCM

Vérifiez vos Acquis

QUESTION 01
Deux conteneurs d'un même pod ne peuvent pas écouter sur le même port.
Pile réseau partagée

Ils partagent l'espace de noms réseau du pod, donc la même adresse et la même table de ports. Le second obtient une erreur de port déjà utilisé.

QUESTION 02
Le champ containerPort d'un manifeste ouvre le port sur le réseau.
Purement indicatif

Il documente l'intention et sert à nommer un port pour un Service. Un conteneur qui écoute sur un port non déclaré reste parfaitement joignable.

QUESTION 03
Un ping qui échoue vers l'IP d'un Service prouve que le service est en panne.
Mauvais outil

L'adresse d'un Service est virtuelle et ne répond généralement pas à l'ICMP. Le test valable est une connexion TCP ou UDP vers le port du service.

QUESTION 04
Sans fichier de configuration dans /etc/cni/net.d, les pods restent en ContainerCreating.
Réflexe de diagnostic

Le runtime ne sait pas connecter le pod au réseau et échoue. Le nœud reste NotReady. C'est le premier répertoire à inspecter sur une panne réseau généralisée.

Étape 08 · Atelier

Atelier 4 : Ausculter le Réseau

Atelier 04 · 30 minutes

Vérifier le contrat réseau sur votre propre cluster

1. Les plages en vigueur
Plage de pods attribuee a votre noeud $ kubectl get node -o jsonpath='{.items[*].spec.podCIDR}{"\n"}' Plage de services, lue dans le manifeste statique de l'API server $ minikube ssh -- sudo grep service-cluster-ip-range \ /etc/kubernetes/manifests/kube-apiserver.yaml Adresse du noeud, vue depuis la VM $ minikube ip La configuration CNI reellement utilisee $ minikube ssh -- "ls -l /etc/cni/net.d/ ; ls /opt/cni/bin/" $ minikube ssh -- sudo cat /etc/cni/net.d/10-calico.conflist
2. Deux pods, une conversation
$ kubectl run n1 --image=nicolaka/netshoot --command -- sleep 3600 $ kubectl run n2 --image=nicolaka/netshoot --command -- sleep 3600 $ kubectl get pods -o wide Depuis n1, joindre n2 par son IP : aucune traduction d'adresse $ kubectl exec -it n1 -- ping -c3 <IP-DE-n2> L'adresse que le pod voit de lui-meme est bien celle vue de l'exterieur $ kubectl exec n1 -- ip -4 addr show eth0 Deux pods peuvent ecouter sur le meme port, contrairement a l'atelier 2 $ kubectl run w1 --image=nginx:1.27 ; kubectl run w2 --image=nginx:1.27 $ kubectl get pods -o wide | grep -E 'w1|w2'
3. Le DNS interne
$ kubectl exec n1 -- cat /etc/resolv.conf Le service de l'API server, joignable par son nom depuis n'importe quel pod $ kubectl exec n1 -- nslookup kubernetes.default.svc.cluster.local $ kubectl get svc -n kube-system kube-dns Qui repond derriere ce service ? $ kubectl get pods -n kube-system -l k8s-app=kube-dns -o wide
4. Provoquer la panne, puis la lire
Mettre CoreDNS a l'arret $ kubectl -n kube-system scale deployment coredns --replicas=0 La resolution echoue, mais l'IP directe repond toujours : le reseau est intact $ kubectl exec n1 -- nslookup kubernetes.default $ kubectl exec -it n1 -- ping -c2 <IP-DE-n2> Retablir $ kubectl -n kube-system scale deployment coredns --replicas=1
Validation

Vous devez pouvoir citer les trois plages d'adresses de votre cluster, montrer le fichier de configuration CNI actif, et avoir constaté que la panne de DNS laisse la connectivité IP intacte. Supprimez w1, w2 et saucisse-1, gardez n1 et n2 pour le module 14.

Étape 09 · Conclusion

Récapitulatif du Module 4

  • Le contrat : communication pod à pod sans NAT, nœuds et pods mutuellement joignables, adresse vue de l'intérieur identique à celle vue de l'extérieur.
  • Une IP par pod, partagée par ses conteneurs qui dialoguent sur localhost et ne peuvent pas réutiliser un même port.
  • CNI : une configuration dans /etc/cni/net.d, des binaires dans /opt/cni/bin. Premier endroit à inspecter sur une panne réseau.
  • Trois plages disjointes : nœuds, pods, services. Choisies avant l'installation, non modifiables ensuite.
  • CoreDNS : résolution en service.namespace.svc.cluster.local, avec l'effet de bord de ndots:5 sur les noms externes.
