Étape 01 · Le problème

Ingress & Gateway API

Exposer dix applications avec dix Services de type LoadBalancer, c'est dix adresses publiques à payer, dix certificats à gérer et dix entrées DNS à maintenir. Avec des NodePort, c'est dix URL en :31427 que personne ne retiendra.

L'Ingress répond à ce besoin : un point d'entrée HTTP unique, qui lit le nom de domaine demandé et le chemin de l'URL, puis oriente la requête vers le bon Service interne. Une seule adresse externe, un seul endroit pour le TLS, autant d'applications que voulu derrière.

La différence de nature avec le module précédent est importante. Un Service travaille au niveau des connexions TCP. Un Ingress travaille au niveau HTTP : il lit les en-têtes, donc il peut décider en fonction de leur contenu.

Étape 02 · Deux objets distincts

La Ressource & le Contrôleur

La ressource Ingress

Un objet Kubernetes qui décrit des règles de routage. Purement déclaratif, il ne fait rigoureusement rien tout seul. Vous pouvez en créer cent sur un cluster nu, aucune requête ne sera routée.

la description

Le contrôleur d'entrée

Un ou plusieurs pods qui surveillent ces objets, reconfigurent un mandataire HTTP en conséquence et reçoivent réellement le trafic. C'est lui qui fait le travail, et il doit être installé séparément.

l'exécution

Cette séparation explique la panne la plus fréquente sur ce sujet : un Ingress créé, accepté par l'API, visible dans kubectl get ingress, et pourtant sans effet. Il manque simplement un contrôleur, ou l'Ingress ne désigne pas la bonne classe.

Le champ ingressClassName désigne quel contrôleur doit prendre en charge la règle. Un cluster peut en héberger plusieurs, par exemple un pour le trafic public et un pour le trafic interne.

$ kubectl get ingressclass $ kubectl get pods -n ingress-nginx Sans resultat a ces deux commandes, aucun Ingress ne fonctionnera
Étape 03 · La règle

Anatomie d'un Ingress

apiVersion: networking.k8s.io/v1 kind: Ingress metadata: { name: routeur } spec: ingressClassName: nginx # quel controleur s'en occupe tls: - hosts: [saucisse.local] secretName: saucisse-tls # Secret de type kubernetes.io/tls rules: - host: saucisse.local # routage par nom de domaine http: paths: - path: /app # routage par chemin pathType: Prefix backend: service: { name: saucisse, port: { number: 80 } } - path: / pathType: Prefix backend: service: { name: site, port: { number: 80 } }

Trois points à retenir. Le backend est toujours un Service, jamais un pod : l'Ingress ne remplace pas le Service, il se pose devant. Le pathType peut valoir Prefix (le chemin commence par) ou Exact, et l'omettre est une source d'ambiguïté. Enfin, le certificat TLS est un Secret ordinaire, et c'est le contrôleur qui termine le chiffrement : le trafic circule ensuite en clair dans le cluster, sauf configuration particulière.

La limite du modèle
L'API Ingress ne sait exprimer que le routage par nom et par chemin. Tout le reste, réécriture d'URL, redirections, limitation de débit, en-têtes, se fait par des annotations propres à chaque contrôleur. Ces annotations ne sont pas standardisées, ce qui rend un Ingress difficilement portable d'un contrôleur à l'autre. C'est précisément le problème que Gateway API vient corriger.
Étape 04 · État de l'art

Ce qui Change en 2026

Un point d'actualité que vous devez connaître avant de conseiller quoi que ce soit en production. Le contrôleur communautaire ingress-nginx, longtemps la référence par défaut et présent sur environ la moitié des clusters, a été retiré par le projet Kubernetes en mars 2026, faute de mainteneurs.

Concrètement : plus aucune version, plus aucun correctif, plus aucun correctif de sécurité. Les installations existantes continuent de fonctionner et les artefacts restent téléchargeables, mais toute vulnérabilité découverte restera ouverte. Le comité de pilotage a été explicite sur l'urgence de migrer.

L'API Ingress elle-même n'est pas dépréciée. Elle est gelée : elle n'évoluera plus, mais elle reste servie et supportée.

Gateway API

Le successeur officiel. Des objets distincts pour l'infrastructure et pour les routes, un modèle par rôles, et le routage avancé enfin standardisé. Implémenté par Envoy Gateway, Istio, Traefik, Cilium.

la cible

Contrôleurs maintenus

Traefik, HAProxy, Envoy Gateway, ou le contrôleur NGINX de F5. Tous gèrent l'API Ingress, aucun n'est un remplacement direct : les annotations diffèrent.

migration courte

Notre atelier

Le module complémentaire de Minikube installe ingress-nginx. Il fonctionne parfaitement pour apprendre l'API, mais ne le déployez pas en production sans en mesurer le risque.

pédagogie
Gateway API en une phrase
Là où l'Ingress mélangeait tout dans un objet, Gateway API sépare les rôles : la Gateway est déployée par l'équipe plateforme avec ses ports et ses certificats, les HTTPRoute sont écrites par les équipes applicatives dans leur namespace. Le routage avancé, comme envoyer 10 % du trafic vers une nouvelle version, s'écrit enfin dans l'API standard au lieu d'annotations propriétaires. Tout nouveau projet devrait commencer directement par là.
Étape 05 · QCM

Vérifiez vos Acquis

QUESTION 01
Un Ingress sans contrôleur installé n'a aucun effet.
Description seule

La ressource est acceptée et stockée, mais rien ne route le trafic. Vérifiez toujours la présence d'une IngressClass et des pods du contrôleur.

QUESTION 02
L'Ingress remplace le Service : il route directement vers les pods.
Il se pose devant

Le backend d'une règle est toujours un Service. L'Ingress ajoute une couche HTTP au-dessus de ce qui existe déjà.

QUESTION 03
Les fonctions avancées d'un Ingress passent par des annotations propres au contrôleur.
D'où le manque de portabilité

Réécritures, limitation de débit, en-têtes : rien n'est standardisé. Changer de contrôleur impose de réécrire ces annotations, et c'est ce que Gateway API corrige.

QUESTION 04
L'API Ingress a été supprimée de Kubernetes en 2026.
Gelée, pas supprimée

C'est le contrôleur communautaire ingress-nginx qui a été retiré. L'API reste servie et supportée, mais elle n'évoluera plus au profit de Gateway API.

Étape 06 · Atelier

Atelier 15 : un Point d'Entrée Unique

Atelier 15 · 35 minutes

Router deux applications derrière un seul nom de domaine

1. Installer le contrôleur
$ minikube addons enable ingress Patientez que les pods soient Running $ kubectl get pods -n ingress-nginx -w $ kubectl get ingressclass
2. Deux services à router
saucisse existe depuis le module 14, site depuis le module 9 $ kubectl expose deployment site --port=80 2>/dev/null ; kubectl get svc saucisse site Un nom de domaine local qui pointe vers le noeud $ echo "$(minikube ip) saucisse.local" | sudo tee -a /etc/hosts $ ping -c1 saucisse.local
3. La règle de routage
$ cd ~/k8s && cat > ingress.yaml <<'EOF' apiVersion: networking.k8s.io/v1 kind: Ingress metadata: { name: routeur } spec: ingressClassName: nginx rules: - host: saucisse.local http: paths: - path: /app pathType: Prefix backend: service: { name: saucisse, port: { number: 80 } } - path: / pathType: Prefix backend: service: { name: site, port: { number: 80 } } EOF $ kubectl apply -f ingress.yaml Attendu : une adresse apparait dans la colonne ADDRESS $ kubectl get ingress routeur $ kubectl describe ingress routeur Deux applications, un seul point d'entree $ curl -s http://saucisse.local/ $ curl -s http://saucisse.local/app
4. Ajouter le TLS
$ openssl req -x509 -nodes -days 30 -newkey rsa:2048 \ -keyout saucisse.key -out saucisse.crt -subj "/CN=saucisse.local" $ kubectl create secret tls saucisse-tls --cert=saucisse.crt --key=saucisse.key $ kubectl patch ingress routeur --type=json -p='[{"op":"add","path":"/spec/tls", "value":[{"hosts":["saucisse.local"],"secretName":"saucisse-tls"}]}]' -k car le certificat est auto-signe $ curl -sk https://saucisse.local/app $ curl -s -o /dev/null -w "%{http_code}\n" http://saucisse.local/app # redirection 308
5. Le diagnostic
Une classe inexistante : l'objet est accepte, rien ne se passe $ kubectl patch ingress routeur -p '{"spec":{"ingressClassName":"absent"}}' $ curl -s -o /dev/null -w "%{http_code}\n" http://saucisse.local/app $ kubectl logs -n ingress-nginx -l app.kubernetes.io/component=controller --tail=20 $ kubectl patch ingress routeur -p '{"spec":{"ingressClassName":"nginx"}}'
Validation

Deux applications doivent répondre sur le même nom de domaine, en HTTP puis en HTTPS, et vous devez savoir nommer les trois vérifications à faire face à un Ingress qui ne route rien : la classe, la présence du contrôleur, et l'existence du Service en backend.

Étape 07 · Conclusion

Récapitulatif du Module 15

  • Un point d'entrée HTTP unique qui route par nom de domaine et par chemin, et termine le TLS.
  • Ressource et contrôleur sont deux choses distinctes. Sans contrôleur, un Ingress ne fait rien.
  • Le backend est toujours un Service. L'Ingress se pose devant, il ne remplace rien.
  • Les fonctions avancées passent par des annotations propres à chaque contrôleur, donc non portables.
  • ingress-nginx est retiré depuis mars 2026. L'API Ingress reste supportée mais gelée. Gateway API est la cible pour tout nouveau projet.
