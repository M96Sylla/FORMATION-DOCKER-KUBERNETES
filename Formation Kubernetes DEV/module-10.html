Étape 01 · Le principe

ConfigMaps & Secrets

Une image doit être identique en développement, en recette et en production. Ce qui change d'un environnement à l'autre est la configuration, et elle doit donc être injectée au démarrage, jamais construite dans l'image.

Kubernetes propose deux objets pour cela, volontairement séparés. La ConfigMap porte les données non sensibles : adresses, ports, niveaux de journalisation, fichiers de configuration complets. Le Secret porte les données sensibles : mots de passe, jetons, clés et certificats.

Techniquement, ces deux objets se ressemblent beaucoup. Ce qui les distingue est le traitement que le cluster leur applique : chiffrement au repos, droits d'accès, absence des journaux, stockage en mémoire plutôt que sur disque.

La limite à connaître
Ces objets sont stockés dans etcd et plafonnés à environ 1 Mio. Ils conviennent à des fichiers de configuration, pas à des jeux de données. Au-delà, il faut un volume.
Étape 02 · Création

Données Portables : la ConfigMap

Une ConfigMap est un simple dictionnaire de clés et de valeurs textuelles. Une valeur peut être un mot, ou un fichier entier de plusieurs centaines de lignes.

Trois facons de la creer $ kubectl create configmap reglages --from-literal=NIVEAU=debug --from-literal=PORT=8080 $ kubectl create configmap site --from-file=nginx.conf $ kubectl create configmap env --from-env-file=variables.env Le resultat, en YAML apiVersion: v1 kind: ConfigMap metadata: { name: reglages } data: NIVEAU: debug PORT: "8080" # toujours des chaines : les guillemets comptent app.properties: | # une valeur peut etre un fichier entier timeout=30 retries=3
Sur le terrain
Une ConfigMap vit dans un namespace et n'est visible que de lui. Un pod ne peut pas référencer une ConfigMap d'un autre namespace, ce qui impose de la dupliquer pour chaque environnement. C'est voulu : cette frontière est la même que celle des droits d'accès.
Étape 03 · Consommation

Utiliser une ConfigMap

1. Une cle vers une variable d'environnement precise env: - name: LOG_LEVEL valueFrom: configMapKeyRef: { name: reglages, key: NIVEAU } 2. Toutes les cles d'un coup envFrom: - configMapRef: { name: reglages } 3. En fichiers, un par cle volumes: - name: conf configMap: { name: site } volumeMounts: - { name: conf, mountPath: /etc/nginx/conf.d } 4. Un seul fichier, sans ecraser le repertoire - { name: conf, mountPath: /etc/nginx/nginx.conf, subPath: nginx.conf }

La différence décisive entre ces formes est le rechargement. Les variables d'environnement sont figées au démarrage du processus : modifier la ConfigMap ne change rien tant que le pod n'est pas recréé. Un volume, lui, est mis à jour automatiquement par le kubelet, avec un délai de l'ordre de la minute. L'application peut alors relire son fichier sans redémarrer, à condition de savoir le faire.

L'exception subPath
Un fichier monté avec subPath n'est jamais mis à jour. C'est une limite technique connue et une source classique de confusion : la ConfigMap change, le fichier dans le pod ne bouge pas. Si vous avez besoin du rechargement, montez le répertoire entier.
Étape 04 · Données sensibles

Les Secrets

Un Secret ressemble à une ConfigMap, avec des valeurs encodées en base64. Disons-le tout de suite, avant que quelqu'un ne le découvre en production : le base64 n'est pas du chiffrement. C'est un encodage, réversible par n'importe qui en une commande.

Ce qui protège réellement un Secret, ce sont trois mesures que l'administrateur doit mettre en place :

  • RBAC (module 12) : restreindre qui a le droit de lire les Secrets d'un namespace. C'est la protection principale.
  • Chiffrement au repos : par défaut, etcd stocke les Secrets en clair. Il faut activer explicitement le chiffrement côté API server, avec une clé locale ou un gestionnaire externe.
  • Hygiène : ne jamais commiter un Secret en clair dans un dépôt Git, et préférer une injection depuis un coffre-fort externe.
Les types les plus courants Opaque # le cas general kubernetes.io/tls # cles tls.crt et tls.key, pour l'Ingress kubernetes.io/dockerconfigjson # acces a un registre prive kubernetes.io/service-account-token # jeton d'identite d'un compte de service
Étape 05 · Consommation

Injecter un Secret

Par variable d'environnement : simple, mais expose env: - name: MYSQL_ROOT_PASSWORD valueFrom: secretKeyRef: { name: mysql-secret, key: password } Par volume : chaque cle devient un fichier, monte en memoire volumes: - name: identifiants secret: secretName: mysql-secret defaultMode: 0400 # lisible par le seul proprietaire volumeMounts: - { name: identifiants, mountPath: /etc/secrets, readOnly: true }

Le montage en volume est préférable pour trois raisons. Le contenu est écrit dans un système de fichiers en mémoire, jamais sur le disque du nœud. Il se met à jour sans recréer le pod. Et surtout, il n'apparaît pas dans l'environnement du processus, alors qu'une variable est lisible par kubectl describe, par les journaux de démarrage, par les rapports de plantage et par tout processus du conteneur.

Sur le terrain
La pratique courante consiste à ne pas stocker les secrets dans Kubernetes du tout. Un opérateur externe (External Secrets, ou l'injection par un agent de coffre-fort) va chercher la valeur dans un gestionnaire dédié et fabrique le Secret dans le cluster à la volée. Le dépôt Git ne contient alors que la référence, jamais la valeur.
Étape 06 · QCM

Vérifiez vos Acquis

QUESTION 01
Les valeurs d'un Secret sont chiffrées par Kubernetes.
Simplement encodées

Le base64 se décode en une commande. La protection vient de RBAC et du chiffrement d'etcd, qui doit être activé explicitement.

QUESTION 02
Une ConfigMap montée en volume est mise à jour sans recréer le pod.
Avec un délai

Le kubelet rafraîchit le contenu, en général en moins d'une minute. L'application doit toutefois savoir relire son fichier. Les variables d'environnement, elles, ne changent jamais.

QUESTION 03
Un fichier monté avec subPath n'est pas rafraîchi quand la ConfigMap change.
Limite connue

Le montage d'un fichier unique casse le mécanisme de mise à jour. Pour bénéficier du rechargement, il faut monter le répertoire complet.

QUESTION 04
Un pod peut référencer une ConfigMap située dans un autre namespace.
Frontière stricte

ConfigMaps et Secrets ne sont visibles que dans leur propre namespace. Il faut les dupliquer, ou utiliser un opérateur qui synchronise.

Étape 07 · Atelier

Atelier 10 : Externaliser la Configuration

Atelier 10 · Partie 1 · 20 minutes

Une ConfigMap sous ses deux formes, et son rechargement

1. Créer et inspecter
$ cd ~/k8s $ kubectl create configmap reglages \ --from-literal=NIVEAU=debug --from-literal=REGION=eu-west $ cat > message.txt <<'EOF' Bonjour, ici la saucisse, version 1. EOF $ kubectl create configmap contenu --from-file=message.txt $ kubectl get configmap reglages -o yaml
2. Les deux modes de consommation dans un même pod
$ cat > conso.yaml <<'EOF' apiVersion: v1 kind: Pod metadata: { name: conso } spec: containers: - name: app image: busybox:1.36 command: ["sh","-c","sleep 3600"] envFrom: - configMapRef: { name: reglages } volumeMounts: - { name: fichiers, mountPath: /etc/conf } volumes: - name: fichiers configMap: { name: contenu } EOF $ kubectl apply -f conso.yaml $ kubectl exec conso -- env | grep -E 'NIVEAU|REGION' $ kubectl exec conso -- cat /etc/conf/message.txt
3. Modifier, et observer qui suit
On change les deux ConfigMaps $ kubectl create configmap contenu --from-literal=message.txt="La saucisse version 2, rechargee." \ --dry-run=client -o yaml | kubectl apply -f - $ kubectl create configmap reglages --from-literal=NIVEAU=info --from-literal=REGION=eu-west \ --dry-run=client -o yaml | kubectl apply -f - Patientez jusqu'a une minute, puis comparez $ kubectl exec conso -- cat /etc/conf/message.txt # a change $ kubectl exec conso -- env | grep NIVEAU # n'a pas change
Étape 08 · Atelier

Atelier 10 : Un Secret en Situation

Atelier 10 · Partie 2 · 25 minutes

Déployer une base MySQL dont le mot de passe n'est écrit nulle part en clair

1. Créer le Secret et vérifier ce qu'il vaut
$ kubectl create secret generic mysql-secret \ --from-literal=password='S4uc1sse-2026' La demonstration qui met tout le monde d'accord $ kubectl get secret mysql-secret -o jsonpath='{.data.password}' | base64 -d ; echo Et dans etcd, sans chiffrement active, c'est aussi lisible $ kubectl get secret mysql-secret -o yaml
2. La base, avec son volume persistant
$ cat > mysql.yaml <<'EOF' apiVersion: v1 kind: PersistentVolumeClaim metadata: { name: mysql-pvc } spec: accessModes: [ReadWriteOnce] resources: { requests: { storage: 1Gi } } --- apiVersion: apps/v1 kind: Deployment metadata: { name: mysql } spec: replicas: 1 selector: { matchLabels: { app: mysql } } template: metadata: { labels: { app: mysql } } spec: containers: - name: mysql image: mysql:8.0 env: - name: MYSQL_ROOT_PASSWORD valueFrom: secretKeyRef: { name: mysql-secret, key: password } - name: MYSQL_DATABASE value: saucisse ports: [{ containerPort: 3306 }] volumeMounts: [{ name: data, mountPath: /var/lib/mysql }] volumes: - name: data persistentVolumeClaim: { claimName: mysql-pvc } EOF $ kubectl apply -f mysql.yaml $ kubectl get pods -l app=mysql -w
3. Se connecter, et constater la fuite
$ POD=$(kubectl get pod -l app=mysql -o jsonpath='{.items[0].metadata.name}') $ kubectl exec -it $POD -- sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "show databases;"' Le mot de passe est visible dans l'environnement du processus $ kubectl exec $POD -- env | grep MYSQL_ROOT Il apparait aussi dans la description du pod, en reference $ kubectl describe pod $POD | grep -A2 MYSQL_ROOT
4. La même chose, en volume
$ kubectl run coffre --image=busybox:1.36 --restart=Never --command \ --overrides='{"spec":{"containers":[{"name":"c","image":"busybox:1.36", "command":["sh","-c","ls -l /etc/secrets; cat /etc/secrets/password; echo; df -h /etc/secrets"], "volumeMounts":[{"name":"s","mountPath":"/etc/secrets","readOnly":true}]}], "volumes":[{"name":"s","secret":{"secretName":"mysql-secret","defaultMode":256}}]}}' Notez le systeme de fichiers : tmpfs, donc en memoire, jamais sur disque $ kubectl logs coffre
Validation

Vous devez pouvoir décoder le Secret en une commande, montrer que MySQL démarre sans mot de passe écrit dans le manifeste, et expliquer pourquoi le montage en volume expose moins que la variable d'environnement. Conservez le déploiement mysql pour le module 13.

Étape 09 · Conclusion

Récapitulatif du Module 10

  • Une image, tous les environnements. La configuration est injectée, jamais construite dans l'image.
  • ConfigMap : dictionnaire de clés et de valeurs, jusqu'à un fichier entier. Limitée au namespace et à environ 1 Mio.
  • Quatre modes de consommation : clé à clé, en bloc, en répertoire, en fichier unique par subPath.
  • Rechargement : les volumes se mettent à jour, les variables d'environnement jamais, et subPath fait exception.
  • Secret : base64 et non chiffrement. La vraie protection est RBAC plus le chiffrement d'etcd. Le montage en volume expose moins que la variable.
