Étape 01 · La matière première

Conteneuriser

Une image est une pile de couches en lecture seule, plus un manifeste JSON qui décrit comment les assembler et quelle commande lancer. Rien de plus. Le format est normalisé par l'OCI, ce qui garantit qu'une image construite avec Docker fonctionne sous containerd, CRI-O ou Podman.

Un conteneur est l'exécution de cette pile, augmentée d'une couche d'écriture temporaire et isolée par les deux mécanismes du noyau observés à l'atelier 2 : les namespaces (ce que le processus voit) et les cgroups (ce qu'il a le droit de consommer).

Kubernetes ne construit pas d'images. Il en consomme. La chaîne de fabrication reste votre affaire, et la qualité de ce que vous fabriquez conditionne directement la fiabilité de ce que vous déployez.

Conséquence directe
La couche d'écriture d'un conteneur disparaît à sa mort. Toute donnée à conserver doit sortir du conteneur, par un volume (module 9) ou par le réseau. Une image bien faite est jetable sans regret.
Étape 02 · Les choix

Options de Conteneur

Trois décisions structurent une image, et chacune se paie longtemps.

L'image de base

Une distribution complète coûte 100 à 300 Mo et une longue liste de vulnérabilités. Alpine descend sous 10 Mo. Une image distroless ne contient que les bibliothèques nécessaires, sans shell.

surface d'attaque

Le contenu

Un processus principal par conteneur. Pas de gestionnaire de services, pas de cron, pas de SSH. Ce qui doit tourner à côté devient un autre conteneur du pod.

module 8

L'identité

Ne jamais s'exécuter en root par défaut. Déclarer un utilisateur non privilégié dans l'image évite d'avoir à le forcer ensuite par un contexte de sécurité.

module 13

Trois conventions complètent ces choix, et Kubernetes les suppose acquises. Les journaux partent sur la sortie standard, jamais dans un fichier interne, sinon kubectl logs ne montre rien. La configuration entre par des variables d'environnement ou des fichiers montés, jamais figée dans l'image. Et l'application doit s'arrêter proprement sur SIGTERM, sans quoi chaque mise à jour coupe des connexions en cours.

Étape 03 · La recette

Le Fichier Dockerfile

Chaque instruction produit une couche, mise en cache. L'ordre des instructions détermine donc directement le temps de reconstruction : ce qui change rarement se place en haut, ce qui change à chaque commit se place en bas.

Construction en deux etapes : on compile, puis on ne garde que le binaire FROM golang:1.23-alpine AS build WORKDIR /src COPY go.mod ./ # change rarement : couche mise en cache COPY main.go ./ # change souvent : place apres RUN CGO_ENABLED=0 go build -o /out/saucisse . FROM alpine:3.20 # l'image finale repart de zero RUN adduser -D -u 10001 app COPY --from=build /out/saucisse /usr/local/bin/saucisse USER 10001 # jamais root par defaut EXPOSE 8080 # documentaire, comme containerPort ENTRYPOINT ["/usr/local/bin/saucisse"]
Sur le terrain
La construction multi-étapes est la seule façon simple d'obtenir une image légère : la chaîne de compilation, ses sources et son cache restent dans l'étape build et ne sont jamais publiés. Ici, on passe d'environ 300 Mo à moins de 20 Mo, et le compilateur n'est pas embarqué en production.
Étape 04 · Les pièges

Cinq Erreurs qui Coûtent Cher

  • L'étiquette latest. Elle ne désigne rien de stable et rend tout déploiement irreproductible. Étiquetez par version, ou mieux, par empreinte de contenu. Un retour arrière sur latest est impossible.
  • Le secret dans l'image. Une clé copiée puis supprimée à l'instruction suivante reste présente dans la couche précédente et lisible par tous. Les secrets se montent à l'exécution (module 10).
  • Le cache de paquets embarqué. Sur une base Debian, terminez l'installation par la suppression de /var/lib/apt/lists, dans la même instruction RUN, sinon la couche a déjà été figée.
  • Le COPY . . sans fichier .dockerignore, qui embarque le dépôt git, les dépendances locales et parfois des identifiants.
  • Le shell comme ENTRYPOINT. Sous forme shell, le processus ne reçoit pas le SIGTERM et l'arrêt se termine par un SIGKILL après le délai de grâce. Utilisez la forme exec, entre crochets.
Politique de téléchargement
Le champ imagePullPolicy vaut IfNotPresent par défaut, sauf si l'étiquette est latest, auquel cas il devient Always. Conséquence pratique : reconstruire une image sans changer l'étiquette ne redéploie rien, le nœud garde sa copie locale.
Étape 05 · La distribution

Faire Entrer une Image dans le Cluster

Une image construite sur votre VM n'est pas visible du nœud Minikube : ce sont deux démons de conteneurs distincts. C'est la première surprise de tous ceux qui débutent avec Minikube, et elle se règle de trois façons.

docker-env

eval $(minikube docker-env) pointe votre client Docker vers le démon du nœud. Tout ce que vous construisez ensuite est immédiatement disponible pour le kubelet.

le plus direct

image load

minikube image load mon-image:v1 transfère une image déjà construite sur la VM vers le nœud. Pratique, mais lent sur les grosses images.

dépannage

Un registre

Un serveur HTTP qui stocke couches et manifestes. La seule méthode qui fonctionne à plusieurs nœuds, et la seule utilisée en production.

notre atelier

Nous prendrons la première voie pour la formation : docker-env, puis un déploiement avec imagePullPolicy: Never, qui interdit tout téléchargement et impose d'utiliser l'image locale. C'est immédiat et il n'y a rien à configurer. Un bonus en fin d'atelier montre la mise en place d'un registre pour ceux qui veulent aller jusqu'au bout de la chaîne.

Sur le terrain
En production, le registre est en HTTPS et authentifié. Les identifiants sont alors stockés dans un Secret de type kubernetes.io/dockerconfigjson, référencé par le champ imagePullSecrets du pod ou du compte de service. Un pod bloqué en ImagePullBackOff vient neuf fois sur dix de ce secret manquant ou périmé.
Étape 06 · QCM

Vérifiez vos Acquis

QUESTION 01
Supprimer un fichier secret dans une instruction RUN ultérieure le retire de l'image.
Les couches persistent

La couche qui contenait le fichier reste dans l'image et se lit avec un simple docker save. La suppression n'ajoute qu'un marqueur dans la couche suivante.

QUESTION 02
Une image construite sur la VM n'est pas visible du nœud Minikube.
Deux démons distincts

Le nœud a son propre moteur de conteneurs. Il faut soit construire directement chez lui avec docker-env, soit transférer l'image, soit passer par un registre.

QUESTION 03
Une application qui écrit ses journaux dans un fichier interne n'apparaît pas dans kubectl logs.
stdout et stderr

Le kubelet ne collecte que les deux sorties standard du processus principal. Un fichier interne au conteneur reste invisible et disparaît avec lui.

QUESTION 04
Une image construite avec Docker doit être reconstruite pour tourner sous containerd.
Format OCI

Le format d'image est normalisé. La même image fonctionne avec Docker, containerd, CRI-O ou Podman, sans aucune modification.

Étape 07 · Atelier

Atelier 5 : Construire l'Image

Atelier 05 · Partie 1 · 25 minutes

Une application, un Dockerfile, une construction dans le nœud

1. Brancher le client Docker sur le nœud
A ne faire que dans ce terminal : la variable disparait a la fermeture $ eval $(minikube docker-env) Preuve que l'on parle bien au demon du noeud : les conteneurs du cluster apparaissent $ docker ps --format '{{.Names}}' | head Pour revenir au demon de la VM : eval $(minikube docker-env -u)
2. L'application
$ mkdir -p ~/k8s/saucisse && cd ~/k8s/saucisse $ cat > go.mod <<'EOF' module saucisse go 1.23 EOF $ cat > main.go <<'EOF' package main import ("fmt"; "net/http"; "os") func main() { v := os.Getenv("APP_VERSION") if v == "" { v = "v1" } h, _ := os.Hostname() http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) { fmt.Fprintf(w, "saucisse %s servie par %s\n", v, h) }) http.HandleFunc("/healthz", func(w http.ResponseWriter, r *http.Request) { w.WriteHeader(200) }) fmt.Println("ecoute sur :8080") http.ListenAndServe(":8080", nil) } EOF
3. Le Dockerfile et la construction
$ cat > Dockerfile <<'EOF' FROM golang:1.23-alpine AS build WORKDIR /src COPY go.mod main.go ./ RUN CGO_ENABLED=0 go build -o /out/saucisse . FROM alpine:3.20 RUN adduser -D -u 10001 app COPY --from=build /out/saucisse /usr/local/bin/saucisse USER 10001 EXPOSE 8080 ENTRYPOINT ["/usr/local/bin/saucisse"] EOF $ docker build -t saucisse:v1 . Comparez la taille de l'image finale avec celle de l'image de compilation $ docker images | grep -E 'saucisse|golang' Test hors Kubernetes, dans le noeud $ docker run --rm -d -p 8080:8080 --name essai saucisse:v1 $ minikube ssh -- curl -s localhost:8080 ; docker rm -f essai
Étape 08 · Atelier

Atelier 5 : Déployer son Image

Atelier 05 · Partie 2 · 20 minutes

Faire tourner l'image dans le cluster, sans registre

1. Déployer avec imagePullPolicy: Never
L'image n'existe dans aucun registre : on interdit tout telechargement $ cd ~/k8s && kubectl run saucisse --image=saucisse:v1 --port=8080 \ --overrides='{"spec":{"containers":[{"name":"saucisse","image":"saucisse:v1", "imagePullPolicy":"Never","ports":[{"containerPort":8080}]}]}}' $ kubectl get pod saucisse -o wide $ kubectl logs saucisse $ kubectl exec n1 -- curl -s http://<IP-DU-POD>:8080
2. Ce qui se passe sans cette précaution
Meme image, mais Kubernetes a le droit d'aller la chercher ailleurs $ kubectl run essai --image=saucisse:v1 Attendu : Running quand meme, car l'image est presente sur le noeud $ kubectl get pod essai Avec une etiquette absente, l'erreur devient explicite $ kubectl run essai2 --image=saucisse:v9 $ kubectl describe pod essai2 | tail -6 $ kubectl delete pod essai essai2
3. Préparer la version 2, pour le module 11
Changez le texte de la ligne fmt.Fprintf dans main.go $ cd ~/k8s/saucisse && docker build -t saucisse:v2 . $ docker images | grep saucisse
Bonus : un vrai registre local
Toujours branche sur le demon du noeud, avec docker-env $ docker run -d --restart=always -p 5000:5000 --name registry registry:2 $ docker tag saucisse:v1 localhost:5000/saucisse:v1 $ docker push localhost:5000/saucisse:v1 $ minikube ssh -- curl -s localhost:5000/v2/_catalog L'image devient alors deployable par son nom complet, sans imagePullPolicy $ kubectl run depuis-registre --image=localhost:5000/saucisse:v1
Validation

L'atelier est réussi si le pod saucisse est Running et si l'appel renvoie la ligne saucisse v1 servie par saucisse. Retenez surtout la règle : sans registre, l'image n'existe que sur ce nœud, ce qui suffit ici mais ne passerait pas à l'échelle. Supprimez le pod saucisse, le module 6 le recréera proprement dans un Deployment.

Étape 09 · Conclusion

Récapitulatif du Module 5

  • Une image OCI est une pile de couches portable entre tous les runtimes. Kubernetes la consomme sans jamais la fabriquer.
  • Choix structurants : base minimale, un processus par conteneur, utilisateur non privilégié, journaux sur la sortie standard.
  • Construction multi-étapes : la chaîne de compilation reste dans l'étape de construction, l'image finale ne contient que le nécessaire.
  • Étiquetage : jamais latest. La politique par défaut ne retélécharge pas une étiquette déjà présente sur le nœud.
  • Sur Minikube : trois façons de faire entrer une image, dont le registre local, seule méthode transposable en production.
Prochaine étape
L'image existe et le cluster sait la télécharger. Le module 6 s'attaque au pod lui-même : le décrire en YAML, y exécuter des commandes, y ajouter un second conteneur, et surtout apprendre à Kubernetes comment savoir si l'application fonctionne vraiment.
